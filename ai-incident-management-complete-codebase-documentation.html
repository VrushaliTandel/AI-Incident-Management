1. Project Overview & Architecture

The AI Incident Management platform is an enterprise-grade IT helpdesk automation system. Users submit IT incidents (text or voice, any language). A multi-tier AI pipeline — built with LangGraph, RAG + ChromaDB, and OpenAI GPT-4o-mini — attempts to resolve the issue through up to three automated tiers before escalating to a human agent.

LayerTechnologyPort
Frontend (UI)Streamlit8501
Backend (API)FastAPI + Uvicorn8000
AI WorkflowLangGraph (StateGraph)in-process
Vector StoreChromaDBon-disk
DatabaseSQLite via SQLAlchemyon-disk
LLMOpenAI GPT-4o-mini / Ollamaexternal
Tier Flow: User Query → RAG (ChromaDB) → L1 Resolution → [Verify?] ├── YES → RESOLVED └── NO → Diagnostics (up to 3 rounds) └── Routing Decision ├── L2 → [Verify?] → YES → RESOLVED │ → NO → L3 → [Verify?] → YES → RESOLVED │ → NO → HUMAN HANDOFF ├── MORE_DIAGNOSTICS → (loop) └── HUMAN_HANDOFF (direct)

Purpose: Conditional edge routing functions. Each function inspects state and returns the name of the next node (or "__end__" to pause and await user input).

backend/graph/workflow.py
LangGraph

Purpose: Assembles the StateGraph — registers all nodes, wires all edges (deterministic and conditional), and compiles it with a MemorySaver checkpointer.

  • build_workflow() — full graph construction; deterministic edges: rag→l1, diagnostics→routing, final_response→persist, handoff→persist, persist→END; conditional edges at l1, routing, l2, l3
  • get_workflow() — @lru_cache(maxsize=1) — returns the singleton compiled graph
MemorySaver is in-process memory. After a server restart the checkpoints are gone. The incident_service uses update_state() to re-seed from DB state, making cross-restart resumption possible.

7. RAG Pipeline — backend/rag/

backend/rag/embeddings.py
RAG

Purpose: Embeddings model factory. Returns an @lru_cache singleton of either OpenAI embeddings or HuggingFace local embeddings.

  • If OPENAI_API_KEY is set → OpenAIEmbeddings (text-embedding-3-small)
  • Otherwise or on fallback → HuggingFaceEmbeddings (sentence-transformers/all-MiniLM-L6-v2, CPU)
backend/rag/loader.py
RAG

Purpose: Document loader for the knowledge base directory. Supports .txt, .md, .pdf, .docx files. Auto-creates default knowledge base guides if the directory is empty.

  • load_documents() — iterates all supported files in the knowledge_base path, tags each doc with source metadata
  • _create_default_knowledge_base() — writes 7 built-in troubleshooting guides (VPN, network, email, auth, server, router, camera) when no docs exist
backend/rag/vectorstore.py
RAG

Purpose: ChromaDB vector store lifecycle management. Loads from disk if it already exists; builds from documents if not (or if force_rebuild=True).

  • get_or_create_vectorstore() — checks for existing chroma.sqlite3 on disk; if empty, calls load_documents(), splits with RecursiveCharacterTextSplitter (800-char chunks, 100 overlap), embeds and persists
  • get_vectorstore() — module-level cached instance; only one ChromaDB connection per process
backend/rag/retriever.py
RAG

Purpose: Thin wrapper around ChromaDB similarity search. Used by rag_node().

  • retrieve_documents(query, k=5) — similarity_search; returns empty list on failure (graceful degradation)
  • retrieve_with_scores() — returns (doc, score) tuples
  • format_context() — formats retrieved docs into [Source N: filename]\ncontent blocks for LLM context injection

8. Services Layer — backend/services/

backend/services/auth_service.py
Service

Purpose: Password hashing and JWT token operations. Uses passlib/bcrypt and python-jose.

  • hash_password() — bcrypt hash
  • verify_password() — bcrypt verify (constant-time)
  • create_access_token() — encodes sub+role+exp into HS256 JWT; default expiry 480 minutes
  • decode_token() — decodes and validates JWT; returns None on JWTError
backend/services/incident_service.py
Service

Purpose: The primary orchestration service. Manages LangGraph workflow execution with DB-backed state persistence across server restarts.

create_new_incident()

Creates the Incident row in DB → builds initial state → streams workflow from "rag" → reads merged checkpoint state → persists to DB → returns state to API router.

resume_incident()

Restores state from DB → applies user answer (verification YES/NO or diagnostic text) → calls workflow.update_state(as_node=tier) to seed the checkpointer → calls workflow.stream(None) to advance → merges final state from checkpoint → persists to DB.

_apply_verification()

Detects which tier is awaiting verification (L3 if l3_analysis set and l3_resolved None; L2 if l2_analysis set and l2_resolved None; otherwise L1) and sets the correct resolved field. Returns (updated_state, as_node).

_apply_diagnostic()

Records answer against the last unanswered diagnostic question. Returns (updated_state, "diagnostics") so graph routes to routing_decision next.

_resume_fallback()

Emergency path: when update_state() or stream(None) fails, creates a fresh thread ID, seeds it at the logical next node, and streams from there — prevents any incident from getting stuck permanently.

backend/services/memory_service.py
Service

Purpose: State construction helpers that bridge the DB persistence model and LangGraph's in-memory state dict.

  • build_initial_state() — creates the zeroed-out state dict for a brand new incident
  • restore_state_from_db() — reconstructs full state dict from a persisted Incident ORM object (used on resume after any server restart)
  • apply_user_verification() — same tier-detection logic as in incident_service (legacy path)
  • apply_diagnostic_answer() — records diagnostic answer in state (legacy path)
backend/services/analytics_service.py
Service

Purpose: Computes all analytics data for the admin dashboard. Runs SQL aggregations and returns a rich analytics dict.

  • get_admin_analytics() — 30-day daily time series, breakdown by resolution level, by status, top-10 users by incident count, avg resolution time overall and per tier, language distribution, multilingual rate
  • _detect_script_language() — classifies a query string using Unicode block regex patterns into: Hindi/Devanagari, Tamil, Telugu, Kannada, Malayalam, Bengali, Gujarati, Arabic/Urdu, Chinese, Japanese, Korean, Cyrillic, or English
backend/services/evaluation_service.py
Evaluation

Purpose: DeepEval integration. Runs 5 RAG quality metrics against a test dataset and persists results to the evaluations table.

  • run_evaluation() — loads dataset.json, creates LLMTestCase objects, runs FaithfulnessMetric, AnswerRelevancyMetric, ContextualRelevancyMetric, ContextualPrecisionMetric, ContextualRecallMetric, saves to DB, returns aggregated scores
  • _mock_evaluation() — fallback that generates plausible deterministic mock scores if DeepEval is not installed
  • get_evaluation_summary() — retrieves latest 5 run summaries plus per-test-case breakdown for the most recent run

13. End-to-End Data Flow

Flow A — Creating a New Incident

1. User types query in frontend/page_modules/new_incident.py 2. frontend/utils/api.py → POST /incidents (with JWT header) 3. backend/api/incidents.py → validates NewIncidentRequest (guardrails in schemas.py) 4. backend/api/deps.py → decodes JWT, fetches user from DB 5. backend/services/incident_service.py → create_new_incident() a. Creates Incident row in SQLite (repository.create_incident) b. Calls memory_service.build_initial_state() c. Calls workflow.stream(initial_state) → graph runs: rag_node → ChromaDB similarity_search (retriever.py) l1_resolution_node → LLM call with RAG context (prompts.py) graph pauses at END (awaiting_user_input=True) d. Reads merged state from MemorySaver checkpoint e. Persists state to SQLite (update_incident) 6. Returns WorkflowResponse to frontend 7. Frontend renders conversation_history via components/chat.py 8. Displays ✅ Yes / ❌ No verification buttons

Flow B — Resuming (User clicks "No, Try More")

1. User clicks ❌ No → frontend sends POST /incidents/{thread_id}/resume {user_input: "No, not resolved.", input_type: "verification_no"} 2. incident_service.resume_incident() a. Loads incident from DB by thread_id b. restore_state_from_db() → reconstructs full IncidentState c. _apply_verification(resolved=False) → sets user_resolved=False, as_node="l1_resolution" d. workflow.update_state(config, state, as_node="l1_resolution") e. workflow.stream(None, config) → graph follows route_after_l1_verification → "diagnostics" diagnostics_node runs → generates Q1 → pauses (awaiting_user_input=True) f. Reads final merged state from checkpoint g. Persists to DB 3. Frontend shows diagnostic question 4. User types answer → POST /incidents/{thread_id}/resume {input_type: "diagnostic"} 5. _apply_diagnostic() records answer 6. Graph runs: routing_decision_node → decides "L2" → l2_resolution_node → pauses 7. User sees L2 steps. Clicks "Yes" → RESOLVED. Clicks "No" → L3. L3 "No" → HUMAN_HANDOFF.

Flow C — Human Handoff Resolution by Admin

1. human_handoff_node sets status=ESCALATED, creates HumanHandoff DB record 2. Admin navigates to Human Handoffs page 3. frontend/page_modules/human_handoffs.py → api.admin_get_handoffs() 4. Admin clicks "Take Ownership" → POST /admin/handoffs/{id}/take-ownership → update_handoff(assigned_to=admin.id, assigned_at=now) 5. Admin adds notes → POST /admin/handoffs/{id}/notes 6. Admin clicks "Mark Resolved" → POST /admin/handoffs/{id}/resolve → update_handoff(resolved_by_agent=True) + update_incident(status="RESOLVED")
